# Cyclic operads intro — the shape layer before the files

This folder starts the source-level Concurrency track at the operadic layer. If you are reading the Concurrency pedagogy from the beginning, read `../00_concurrency_intro.md` first. That file gives the practical picture: actors having typed conversations, protocols, local views, consensus artifacts, and the eventual relation to the ModalHoTT side.

The Agda files explained here are not yet about actors, payloads, proofs, or session syntax directly. Actors are the opaque participants that appear later in the Sites folder. Payloads and session syntax are the typed content that appears later in the Algebras folder. This folder is about *interaction shape*: how a primitive interaction has boundary positions, how those positions can be rotated, how two interactions are glued together, and which equations make those gluings behave coherently.

The short version:

- `Ports.agda` fixes the boundary-position arithmetic.
- `RawCyclicOperad.agda` defines the raw generated syntax: one binary generator, substitution, and rotation.
- `PortGluing.agda` and `PortRotation.agda` handle the bookkeeping of surviving ports.
- `CyclicAssociative.agda` adds the real laws: associativity and cyclic equivariance.

That sequence looks low-level because it is. The project is not importing a ready-made operad library and then gesturing at applications. It is building the small cyclic operad artifact directly, with the exact port convention the later algebra files need.

## Why operads show up here

An operad is a formal way to talk about operations that can be plugged into other operations. The familiar picture is: an operation has several input slots and one output slot; plugging one operation into an input slot of another produces a bigger operation.

For this project, the important part is not "many inputs" by itself. The important part is *composable interaction*. We want a small formal object that can say: here is a primitive interaction, here are its boundary positions, here is how one interaction is substituted into another, and here are the equations saying that the order of building a composite does not introduce fake distinctions.

> **References**
> - [nLab: operad](https://ncatlab.org/nlab/show/operad) — the general "operations with many inputs" setting.

The particular object here is a cyclic operad. In an ordinary operad, the output is special. In a cyclic operad, the boundary positions are treated cyclically: rotate the picture, and what used to be viewed as the output can be viewed as another boundary slot. This is why a binary generator has three ports total. It has two ordinary inputs plus the output boundary, now all arranged around one cyclic boundary.

> **References**
> - [nLab: cyclic operad](https://ncatlab.org/nlab/show/cyclic+operad) — operads where inputs and output are related by cyclic symmetry.

The project uses this because the Concurrency side needs a formal home for perspective-swap behavior without collapsing cyclic rotation into session duality. Cyclic rotation has order `n + 1`: on three ports, rotating three times returns you to the start. Session duality is involutive: doing it twice returns you to the start. Those are related later, but they are not the same operation.

## The current object: `O_1`

The operad being built in this folder is the small current commitment often called `O_1` in the workflow notes: the cyclic operad generated by one binary operation.

The generator is called:

```agda
gen : O 2
```

Read `O 2` as "the type of binary operations." Because the operad is cyclic, this binary operation has three boundary ports. That three-port shape is the trinion picture: one primitive interaction with three places where the outside world can attach.

This is deliberately minimal. There is no actor identity inside `O_1`, no payload, no message syntax, no session type. Those belong in later layers. `O_1` is the shape skeleton that those later layers can interpret.

So if the implementation story starts with actors and conversations, why does the Agda story start here? Because shape is the common interface. Actors participate in interactions, protocols type the content of interactions, and future conversation-promotion will turn completed interaction patterns into new units. The shape has to be stable before any one interpretation is attached to it.

## Arity and ports

The folder uses one convention everywhere:

```text
an n-ary operation has n + 1 cyclic ports
```

So:

- an arity-2 operation has 3 ports;
- an arity-3 operation has 4 ports;
- in general, `O n` operations have `Port n` boundary positions.

The Agda definition is:

```agda
Port n = Fin (suc n)
```

`suc n` means `n + 1`. `Fin k` is the finite type with exactly `k` inhabitants: the type-theoretic version of `{0, 1, ..., k-1}`. So `Port 2 = Fin 3`: the three boundary positions of the binary generator.

The inhabitants are written in successor notation:

```agda
fzero
fsuc fzero
fsuc (fsuc fzero)
```

Those are the three values of `Fin 3`. The notation is clunky, but it prevents out-of-range mistakes. A value of `Fin 3` cannot be accidentally equal to `3`; the type rules it out.

> **References**
> - [Cubical Agda: `Cubical.Data.Fin`](https://formal.github.io/cubical/Cubical.Data.Fin.Base.html) — finite types in the cubical library.

## Rotation is modular arithmetic

Ports are arranged cyclically, so rotating a port is modular arithmetic. The operation:

```agda
_+ₘ_
```

is modular addition on `Fin`. If there are three ports, adding one moves to the next port, adding another moves to the next, and after the third step we are back at the start.

The zero rotation is:

```agda
fzero
```

The inverse rotation is written in the Agda library as:

```agda
-ₘ_
```

`Ports.agda` renames this to:

```agda
port-inv
```

That rename matters for readability. Later proofs should read as "rotate by the inverse port offset," not as "apply the finite arithmetic library's additive inverse."

> **References**
> - [Cubical Agda: `Cubical.Data.Fin.Arithmetic`](https://formal.github.io/cubical/Cubical.Data.Fin.Arithmetic.html) — modular arithmetic on finite types.
> - [nLab: cyclic group](https://ncatlab.org/nlab/show/cyclic+group) — the abstract group behind modular rotation.

## Generated syntax and built-in equations

`RawCyclicOperad.agda` defines `O` as a higher inductive type. For this folder, the useful meaning is simple: the data declaration can generate both operations and equations between operations.

Ordinary constructors generate terms:

```agda
gen   : O 2
compₒ : ...
rot   : ...
```

Path constructors generate equations:

```agda
rot-zero    : rot fzero a ≡ a
rot-compose : rot i (rot j a) ≡ rot (i +ₘ j) a
```

The equality symbol `≡` is Agda's path/equality type. In prose we will often read it as "equals," but technically it is a type whose inhabitants are witnesses of equality. When an Agda file proves an equality, it is constructing one of those witnesses.

> **References**
> - [The HoTT Book](https://homotopytypetheory.org/book/) — Chapter 6 introduces higher inductive types.
> - [nLab: higher inductive type](https://ncatlab.org/nlab/show/higher+inductive+type)

The raw operad also includes:

```agda
trunc : {n : ℕ} (x y : O n) (p q : x ≡ y) → p ≡ q
```

This says each `O n` is set-truncated. We allow equations between operations, but we do not study higher-dimensional differences between proofs of those equations. That keeps this object close to ordinary algebraic syntax. The project is not building an ∞-operad here.

## What substitution does

Substitution is named:

```agda
compₒ
```

The small `ₒ` keeps it distinct from cubical Agda's own `comp`, which means Kan composition and belongs to the underlying cubical machinery.

Conceptually, `compₒ i j a b` glues port `i` of operation `a` to port `j` of operation `b`. The glued ports disappear as external boundary positions; the surviving ports form the boundary of the composite operation.

For positive arities, the file uses this shape:

```agda
O (suc l) → O (suc r) → O (suc (l + r))
```

The positive-arity restriction avoids a bad nullary edge case in the port-splitting equivalence. It does not remove any operation reachable from the current generator, because `gen : O 2` and composing positive-arity operations keeps us positive.
